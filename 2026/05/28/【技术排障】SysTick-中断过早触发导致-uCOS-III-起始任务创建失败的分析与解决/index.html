【技术排障】SysTick 中断过早触发导致 μC/OS-III 起始任务创建失败的分析与解决

发表于 2026-05-28 更新于 2026-05-30 分类于 嵌入式开发

在手持打印机项目调试过程中，发现部分设备无法正常运行。经排查，问题源于起始任务创建失败。分析表明，在 μC/OS-III 系统初始化阶段，由于 SysTick 定时器过早启动，导致中断嵌套计数器 OSIntNestingCtr 的值不为零，从而影响了起始任务的正常创建。

一 问题描述

系统初始化流程如下：

在 app_init() → main_task_create() 中创建起始任务时，OSTaskCreate() 返回错误码 OS_ERR_TASK_CREATE_ISR，表明系统检测到当前处于中断上下文，起始任务无法创建，导致系统无法启动。

关键现象：当屏蔽 cpu_init() 中的 enable_global_irq() 函数后，程序能够正常运行。

二 问题分析

当系统变量 OSIntNestingCtr（中断嵌套计数器）的值不为0时，OSTaskCreate() 函数会拒绝创建任务，并返回 OS_ERR_TASK_CREATE_ISR。

2.1 OSIntNestingCtr 的作用机制

  • 递增操作：在 SysTickTimer 的中断服务函数 OS_CPU_SysTickHandler 中，会执行 OSIntNestingCtr++
  • 递减操作：仅当操作系统处于运行状态（OSRunning == OS_STATE_OS_RUNNING）时，在 SysTickTimer 的中断退出处理中才会执行 OSIntNestingCtr--
  • 初始化：在 OSInit() 函数中会将 OSIntNestingCtr 初始化为0

2.2 问题时序分析

  1. 过早开启定时器：在 UCOSIII_BSP_Init() 中过早开启了 SysTickTimer
  2. 中断触发风险：从 UCOSIII_BSP_Init() 执行完毕到 OSStart() 执行之前的时间窗口内：
    • SysTick 中断可能被触发
    • 进入 OS_CPU_SysTickHandler 执行 OSIntNestingCtr++
    • 由于此时 OSRunning != OS_STATE_OS_RUNNING，不会执行 OSIntNestingCtr--
  3. 计数器累积：即使 OSInit() 已将 OSIntNestingCtr 重置为0，但在 main_task_create() 执行期间，SysTick 中断仍可能被触发，导致 OSIntNestingCtr 值增加且无法减少
  4. 任务创建失败：当 OSTaskCreate() 检测到 OSIntNestingCtr ≠ 0 时，判定为在ISR上下文中创建任务，因此返回错误

三 解决方法

确保操作系统起来之前，滴答定时器是关闭的

调整初始化顺序，将 SysTick 定时器的启动时机推迟到操作系统启动之后：

或者在 UCOSIII_BSP_Init() 中不要立即启动 SysTick，而是在第一个任务中调用 OS_CPU_SysTickInit() 来启动滴答定时器。

四 总结

这个问题的核心在于中断与操作系统状态的时序配合。在 μC/OS-III 中，OSIntNestingCtr 是判断当前是否处于中断上下文的关键标志，而 SysTick 中断的处理逻辑与操作系统运行状态紧密耦合。因此，在系统完全初始化并启动之前，必须确保 SysTick 定时器处于关闭状态，避免中断嵌套计数器异常累积导致任务创建失败。
